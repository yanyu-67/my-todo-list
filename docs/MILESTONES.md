# 待办事项管理系统实施里程碑

## 1. 文档目的

本文档用于指导“我的待办事项”项目从零开始实现，明确每个阶段要完成的工作、前置条件和验收标准。项目采用前后端分离架构，后端提供 RESTful API，前端提供管理界面，数据库使用 PostgreSQL。

## 2. 项目目标与范围

### 2.1 最终目标

交付一个可以本地运行的待办事项管理系统，用户能够注册或登录后查看、创建、编辑、完成和删除自己的待办事项；后端负责身份认证和权限校验，前端负责交互和页面展示。

### 2.2 技术约束

- 后端：Java 17、Spring Boot 4.1.1、Spring MVC、Spring Data JPA、Spring Security、JWT、Maven。
- 数据库：PostgreSQL，使用 JPA/Hibernate 访问数据。
- 前端：Vue 3、Vite、Vue Router、Pinia、Element Plus、Axios。
- 测试：JUnit 5、Spring Boot Test。
- 接口：RESTful 风格，使用统一 JSON 响应格式。
- 版本管理：Git。
- 本阶段不实现 Docker、云部署、微服务、Redis、消息队列和 CI/CD。

## 3. 建议的实施顺序

```text
工程初始化与接口约定
  ↓
数据库与实体模型
  ↓
基础后端 API
  ↓
用户认证与权限控制
  ↓
前端基础框架与登录
  ↓
待办事项页面与 API 联调
  ↓
测试、文档和最终验收
```

后续阶段应尽量以前一阶段的验收通过为前提。接口格式、实体字段和权限规则一旦确定，应优先通过文档和测试固定下来，减少前后端联调时的反复修改。

## 4. 里程碑总览

| 编号 | 里程碑 | 主要结果 |
| --- | --- | --- |
| M1 | 开发环境与工程骨架 | 后端、前端和数据库可以独立启动 |
| M2 | 数据库与持久化层 | 用户和待办事项能够通过 JPA 持久化 |
| M3 | 待办事项基础 API | 完成待办事项的增删改查及状态管理 |
| M4 | 登录认证与权限控制 | JWT 登录、接口鉴权和数据隔离完成 |
| M5 | 前端应用骨架 | Vue 页面、路由、状态和请求层完成 |
| M6 | 前端业务功能与联调 | 登录、列表、编辑和操作流程可用 |
| M7 | 测试、优化与交付 | 测试通过、文档齐全、项目可本地运行 |

## 5. 分阶段实施计划

### M1：开发环境与工程骨架

#### 工作内容

1. 检查并准备 Java 21、Maven、Node.js、npm 和 PostgreSQL。
2. 创建 Spring Boot 3.x 后端项目，配置 Web、Validation、JPA、Security、JWT 相关依赖，并保留 OpenAPI 文档依赖。
3. 创建 Vue 3 + Vite 前端项目，安装 Vue Router、Pinia、Element Plus 和 Axios。
4. 建立清晰的目录结构，例如后端按 `controller`、`service`、`repository`、`entity`、`dto`、`security` 和 `exception` 分层，前端按 `views`、`components`、`stores`、`api` 和 `router` 分层。
5. 配置本地数据库连接、前端 API 基础地址和跨域策略。敏感配置放在本地配置文件或环境变量中，不提交真实密码。
6. 初始化 Git 仓库和基础 `.gitignore`，提交一个只包含工程骨架的版本。

#### 验收标准

- 后端能够启动并返回健康检查或基础测试接口。
- 前端能够启动并显示 Vue 页面。
- 后端能够成功连接 PostgreSQL。
- 前端可以通过 Axios 访问后端测试接口。

### M2：数据库与持久化层

#### 工作内容

1. 创建用户实体和待办事项实体，并建立用户与待办事项的一对多关系。
2. 为用户设计必要字段：唯一用户名或邮箱、密码哈希、角色（如需要）和创建时间。
3. 为待办事项设计必要字段、非空约束、长度约束和默认完成状态。
4. 创建 Spring Data JPA Repository，封装按用户查询、按 ID 查询和删除等操作。
5. 配置实体关系的加载策略和级联策略，避免返回待办事项时意外暴露用户密码等敏感字段。
6. 准备本地初始化数据或测试数据，但不得把真实账号密码写入版本库。

#### 验收标准

- 应用启动时能够正常创建或校验数据库表结构。
- 能够通过 Repository 保存、查询、更新和删除用户及待办事项。
- 查询某个用户的任务时不会返回其他用户的数据。
- 密码字段不会以明文保存或出现在 API 响应中。

### M3：待办事项基础 API

#### 工作内容

1. 创建待办事项 DTO，避免 Controller 直接接收或返回实体对象。
2. 实现待办事项 API，建议包括：
   - `GET /api/todos`：查询当前用户的任务列表。
   - `GET /api/todos/{id}`：查询任务详情。
   - `POST /api/todos`：创建任务。
   - `PUT /api/todos/{id}`：更新任务。
   - `PATCH /api/todos/{id}/complete`：切换或设置完成状态。
   - `DELETE /api/todos/{id}`：删除任务。
3. 在 Service 层实现业务规则，所有任务操作都必须绑定当前登录用户。
4. 增加请求参数校验，例如标题必填、长度合理、日期格式正确。
5. 增加全局异常处理，统一处理校验异常、资源不存在和业务异常。
6. 在 Controller 或 OpenAPI 注解中补充接口说明、参数和响应示例。

#### 验收标准

- 使用 API 工具可以完整走通任务的创建、查询、修改、完成和删除流程。
- 无效请求能够返回明确且统一格式的错误信息。
- 通过任务 ID 访问其他用户的任务时不会泄露数据，应返回无权访问或资源不存在。
- API 文档能够反映当前实现。

### M4：登录认证与权限控制

#### 工作内容

1. 实现用户注册或预置用户创建流程，密码使用安全哈希算法保存。
2. 实现登录接口，例如 `POST /api/auth/login`，校验用户名和密码后签发 JWT。
3. 实现 JWT 解析、签名校验、过期校验和 Spring Security 认证上下文设置。
4. 配置公开接口和受保护接口：登录及注册接口可公开，任务接口必须登录后访问。
5. 实现当前用户识别，Service 层以认证上下文中的用户为准，而不是信任前端传入的 `userId`。
6. 配置密码错误、Token 缺失、Token 过期和权限不足时的统一响应。
7. 配置开发环境跨域规则，并确认生产环境不会使用过宽的允许来源配置。

#### 验收标准

- 正确账号密码可以登录并获得 JWT，错误密码不能登录。
- 未携带 JWT 访问受保护 API 会被拒绝。
- Token 过期或签名错误时会被拒绝。
- 用户只能读写自己的任务。
- 前端路由守卫即使被绕过，也不能替代或削弱后端鉴权。

### M5：前端应用骨架

#### 工作内容

1. 搭建 Vue Router 路由，至少包括登录页、首页和编辑/新建任务页。
2. 使用 Pinia 管理登录用户、Token 和登录状态。
3. 创建 Axios 实例，集中配置 API 地址、请求头和响应错误处理。
4. 增加请求拦截器，为受保护请求自动附加 `Authorization: Bearer <token>`。
5. 增加响应拦截器，统一处理 401，例如清理登录状态并跳转登录页。
6. 使用 Element Plus 搭建基础布局、导航、表单、表格或卡片列表、确认对话框和消息提示。
7. 根据项目截图或既定设计，先完成页面结构，再补充视觉细节和响应式处理。

#### 验收标准

- 未登录访问首页会跳转登录页。
- 登录状态刷新后能够按设计恢复或安全失效。
- Axios 能够正确附加 Token，并能处理登录失效。
- 各页面可以在 Vue 应用中通过路由正常访问。

### M6：前端业务功能与联调

#### 工作内容

1. 实现登录表单、加载状态、校验、错误提示和登录成功跳转。
2. 实现首页任务列表，展示标题、描述、截止日期、完成状态和操作按钮。
3. 实现新建和编辑任务表单，复用表单组件或保持字段规则一致。
4. 实现完成/取消完成、删除任务，并在操作成功后更新列表或重新加载数据。
5. 处理空列表、加载中、接口失败、网络断开和重复提交等状态。
6. 逐项对照 API 文档完成前后端联调，修正字段命名、时间格式、状态码和错误结构差异。
7. 检查页面刷新、浏览器后退、直接访问受保护 URL 和 Token 过期等边界流程。

#### 验收标准

- 用户能够从登录页进入首页并完成完整任务管理流程。
- 新建、编辑、完成和删除操作的结果与数据库一致。
- 前端不会把其他用户任务显示出来。
- 失败操作有可理解的提示，页面不会因异常响应而崩溃。
- 登录页、首页和编辑任务页达到项目预期的基本视觉结构。

### M7：测试、优化与交付

#### 工作内容

1. 为 Service 层和关键业务规则编写 JUnit 5 单元测试。
2. 使用 Spring Boot Test 编写 Repository 或 API 集成测试，覆盖认证和权限边界。
3. 至少测试以下场景：登录成功、登录失败、未认证访问、用户数据隔离、参数校验、任务 CRUD、状态切换和删除不存在的任务。
4. 检查前端控制台错误、网络请求、表单校验、空状态和异常状态。
5. 检查代码格式、命名、重复逻辑、敏感信息和未使用依赖。
6. 更新 README 或新增开发说明，记录启动顺序、数据库配置、测试命令和 API 文档地址。
7. 使用干净环境按文档重新启动后端、前端和数据库，完成一次端到端验收。

#### 验收标准

- 后端测试全部通过，关键权限规则有自动化测试保护。
- 前端构建成功，没有阻塞性的运行时错误。
- 新开发者按照文档能够完成本地启动。
- 核心用户流程和异常流程均通过验收。
- Git 工作区仅包含与本项目相关的文件和变更。

## 6. 推荐的 API 与页面交付顺序

为了尽早得到可运行成果，可以按下面顺序逐步交付：

1. 后端健康检查。
2. 用户创建和登录 API。
3. 带 JWT 的任务列表查询。
4. 任务创建与详情查询。
5. 任务编辑、完成和删除。
6. 前端登录页。
7. 前端任务列表页。
8. 前端新建/编辑页。
9. 异常处理、权限测试和界面完善。

每完成一项，都应保留一个可以运行或验证的 Git 提交，提交信息应说明本次完成的功能。

## 7. 风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| 前后端字段或响应格式不一致 | 以需求文档固定接口约定，使用 DTO 和 OpenAPI 文档 |
| 越权访问其他用户任务 | 所有查询和修改均按当前认证用户过滤，并编写权限测试 |
| JWT 配置不安全 | 使用环境配置保存密钥，校验签名和过期时间，不记录 Token 到日志 |
| 实体对象直接暴露敏感字段 | 使用 DTO，禁止直接返回 User 实体 |
| 页面只覆盖成功状态 | 明确实现加载、空数据、失败、401 和重复提交状态 |
| 一开始扩展过多功能 | 遵循本期范围，不引入部署、缓存、消息队列等非必要组件 |
| 本地环境差异导致无法启动 | 在交付前按 README 从零执行一次启动和测试流程 |

## 8. 最终完成定义

满足以下条件时，项目可视为第一版完成：

- 后端使用 Java 21 + Spring Boot 3，数据访问通过 Spring Data JPA 完成。
- PostgreSQL 中能够持久化用户和待办事项数据。
- 登录、JWT 认证和后端接口权限校验可用。
- 用户能够在前端完成待办事项的增删改查和完成状态管理。
- API 使用 RESTful 风格和统一 JSON 响应格式，并有 OpenAPI 说明。
- 核心业务、认证和权限边界有 JUnit 5 / Spring Boot Test 覆盖。
- 前后端能够按照项目文档在本地启动和验证。
- 未引入 README 明确排除的基础设施和额外复杂度。
